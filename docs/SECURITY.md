# Security Architecture and Policy

## Security Model

AI Browser enforces a defense-in-depth security model across five boundaries:

### 1. Web Sandbox Boundary
- Remote websites are loaded in isolated `WebContentsView` instances with:
  - `sandbox: true`
  - `contextIsolation: true`
  - `nodeIntegration: false`
  - `webSecurity: true`
  - `allowRunningInsecureContent: false`
- Remote web pages cannot access Electron APIs, Node.js runtime, host filesystems, or internal IPC channels.

### 2. Debugger Port Isolation
- The application **never** enables `--remote-debugging-port` or exposes CDP sockets over loopback or local network adapters.
- All CDP interactions occur exclusively via Electron's internal `webContents.debugger` API inside the main process.

### 3. IPC Channel Validation
- Renderer processes (`Toolbar`, `Sidebar`, `Assistant`) run with isolated contexts.
- IPC invocations are routed through typed preload wrappers (`window.electronAPI`).
- The main process validates sender frame IDs and verifies that requests originate only from trusted internal URLs (`http://localhost:5173` in development or `file://.../index.html` in production).

### 4. Sidecar Authentication & Boundary Isolation
- The Python FastAPI backend binds exclusively to `127.0.0.1`.
- A per-session cryptographically random 256-bit token is generated by Electron upon launch and required for all HTTP and RPC requests.
- Python processes communicate browser actions over private standard streams (`stdin`/`stdout`), ensuring zero network attack surface for automation RPC.

### 5. Credential & Data Protection
- Secrets and API keys (such as NVIDIA NIM or OpenAI keys) are stored using Electron `safeStorage`, which uses Windows DPAPI (Data Protection API) for encryption at rest.
- Passwords, cookies, session tokens, and input elements with `type="password"` are excluded from AI prompts and observation snapshots.
